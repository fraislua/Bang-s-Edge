# agy 委任手順書

## 1. 委任するかの判断
- [ ] 委任規模の判断: 数行〜十数行の修正は往復の時間(2〜4分)に見合わないため、Brainが直接行う(例: 定数変更、軽微なバグ修正)。複数ファイルに跨る変更、まとまった新規実装や骨組み作成、描画や座標変換処理など、往復時間を正当化できる規模の場合に委任する。
- [ ] 過去実績の確認: 委任前に `docs/model-experiment-log.md` を確認し、類似タスクの成否・モデル・effort実績を参考にする。
- [ ] モデル選択の実績(成功例と失敗例):
  - 仕様が数値まで確定している実装: 軽量モデル(`gemini-3.8-flash-high`)で通る(骨組み作成、大規模実装、新要素追加、座標変換などで成功)。ただし仕様に「毎フレーム」等と書くとそのままコード化されフレームレート依存バグになるため、仕様側の表現に注意する。
  - 設計(数式やバランス): agy経由の `claude-opus-4-6-thinking` は構造や根拠の記述は優秀だったが、数値的整合性に致命的欠陥が2件あり**部分的**な結果だった。一方、discord-ai-hub経由の `gpt-5.6-sol` は平衡個数を解析的に予測して実測とほぼ一致しており、**数式の設計相談はまずGPT系統(無料枠)を試す価値がある**(`docs/handoff.md` §7)。どのモデルの設計でも数式の整合性は必ず検算する。設計は高性能モデル・実装は軽量モデルという分離が成立する。
  - 感性的な領域(音色など): 指示が抽象的だと軽量モデルでは手戻りになる(「ホワイトノイズのバースト」程度の指示では、実装は正しいが聴感が不足する**部分的**な結果だった)。ただしBrain側が物理パラメータ(周波数・時定数・ゲイン比・各層の役割など)まで具体化・数値化して渡すなら軽量モデルで実装できる。

## 2. プロンプトの書き方
- [ ] 冒頭の役割明記: 冒頭に `[実装]` または `[監査]` を明記する。`--add-dir` を指定すればワークスペースルートの `AGENTS.md` が自動で読み込まれ基本方針・品質基準が反映されるため、プロンプトには役割と対象だけ書けばよい。
- [ ] ターミナルコマンド実行禁止の明記: ヘッドレスモードのagyはターミナルコマンドを実行できず出力ゼロで失敗するため、「ターミナルコマンドは一切実行せず、ファイル編集ツールのみで作業してください」と明記する(`--dangerously-skip-permissions` は任意コマンドの自動承認になり危険なため使わない)。
- [ ] 対象ファイルの限定と厳守事項: 変更してよいファイルを限定し(他ファイルを破壊させない)、厳守事項や禁止事項は数式や数値(座標、周波数、ゲイン、定数名等)で具体的に指定する。
- [ ] 仕様表現の注意: 仕様の表現がそのまま実装されるため、「毎フレーム」のような記述は避け、時間ベースの減衰式(`Math.pow(DAMPING, dt * 60)`)などフレームレートに依存しない表現で指定する。
- [ ] 要約・整理タスクでの条件保持指示: 要約・整理のタスクでは、事実を足さなくても元資料にある条件や優先順位が抜け落ちて意味が変わることがある(2026-09-11実績)ため、「条件ごと残す(〜の場合は、〜なら、ただしを落とさない)」ようプロンプトで明示する。
- [ ] Unity固有の約束事の明記(Unityの描画・UIを頼むとき): JSなど別環境の数値を正しく写しても見た目が崩れる誤りが3回起きた(2026-09-11)。プロンプトに次を書く。(1) 子の`GameObject`は親の拡大率を引き継ぐので、大きさを変える部品同士は兄弟にする (2) 9スライスの枠の太さは`Canvas`の`referencePixelsPerUnit`(既定100)基準で測られるので、スプライトのpixelsPerUnitはそれに合わせる (3) 実行時に作るテクスチャの色は不透明度を掛けずに書く。詳細は`docs/dev-notes.md`。
- [ ] 既存の長いメソッドへの追記を頼むとき: agyはコンパイルできないため、同じメソッド内のローカル変数名の重複(CS0128)に気づけない(2026-09-11、`GameHud.BuildHudHierarchy`で`bgRt`・`fillRt`が重なった)。「追加するローカル変数には機能名の接頭辞を付ける(例: `sliderBgRt`)」とプロンプトに書く。

## 3. 呼び出し方
- [ ] 基本コマンドの形式:
  - 実装委任: `agy --model <model> --mode accept-edits --add-dir "<リポジトリの絶対パス>" -p $prompt`
  - 監査呼び出し: `agy --model <model> --add-dir "<リポジトリの絶対パス>" -p $prompt`
  - `--add-dir` には必ず絶対パスを指定する。
- [ ] 安全装置としてのモード指定: agyはプロンプトの禁止文だけでは自己判断による実装フェーズへの移行を抑止できないことがある。書き込ませたくない呼び出し(監査・提案のみ)では `--mode accept-edits` を付けないことが権限側の実質的な安全装置になる。
- [ ] 使わないオプションとその理由:
  - `--new-project`: Antigravityのプロジェクト状態ファイル(`antigravity_state.pbtxt`)が更新されプロジェクト一覧が肥大化するため使わない。
  - `--agent`: 検出に `--new-project` が必要で肥大化を招くため使わない(`--add-dir` で `AGENTS.md` が自動読込されるため不要)。
  - `--dangerously-skip-permissions`: 任意コマンドの自動承認になり危険なため、必要になるまで使わない。
- [ ] PowerShell 5.1 とバックグラウンド実行:
  - WindowsのPowerShell 5.1から呼ぶ場合、引数内のダブルクォート破損を避けるため本文はかぎ括弧を使い、単一引用のヒアドキュメント(`@'` から `'@` まで)で変数に入れてから `-p` に渡す(2026-09-11にこの形で2回成功)。
  - 1回の委任は数分(2〜4分)かかるため、Claude Codeではバックグラウンド実行にして、完了通知を待つ間に検証の準備を進める。

## 4. 結果の検証(報告を信用しない)
- [ ] 実物での検証: agyの報告テキストを完了の根拠とせず、必ず実物(`git status`、タイムスタンプ、ファイル内容)で検証する。
- [ ] 報告と実態の食い違いの警戒: `--mode accept-edits` なしの呼び出しで、実際にはファイルが1つも作成・変更されていないにもかかわらず「承認されたので実装に進めます」と虚偽の完了報告をした実例がある。
- [ ] ワークスペース外の成果物回収: 設計提案書などの成果物がワークスペース内ではなく `~/.gemini/antigravity-cli/brain/<会話ID>/` 配下に書かれることがある。応答内の `file:///` リンクを確認し、必要ならそこから読み出す。
- [ ] 実コードの挙動検証: 可能なら本物のコードをNodeで動かして挙動で検証する(`vm.runInThisContext` で読み込み、CanvasやDOM、`requestAnimationFrame` をスタブして手動で `update()` を実行。手順は `docs/dev-notes.md` 参照)。物理ロジックの再実装ではなく実コードの挙動レベルで仕様通りか確認できる。
- [ ] 移植の数値一致テスト: 別言語への移植を委任するときは、**委任の前に**移植元を固定シードで動かした基準データと、それと突き合わせるテストを用意しておく(`tools/sim-harness/golden.js`)。委任先の報告を読まずに合否を判定でき、C#移植では600行が一発で通ったことをこれで確認した。
- [ ] 数式設計の検算: 数式を含む設計は、重いモデル(`claude-opus-4-6-thinking` 等)の出力であってもBrain自身で検算する(分母定義、到達不能なしきい値、速度減衰項の有無など)。
- [ ] 要約・整理タスクの検証: 要約・整理タスクでは、事実の追加がないかだけでなく、元資料の条件付きの記述が条件ごと残っているか(〜の場合は、〜なら、ただし)を確認する。

## 5. 記録(後回しにしない)
- [ ] 実験ログの追記: 委任後は結果を `docs/model-experiment-log.md` に1行追記する(列構成: `| 日付 | タスク内容/種別 | 委任先 | モデル | effort | 結果 | 選択理由 | 備考 |`)。
- [ ] 実装メモの追記: agyから得られた気づき、ツールの挙動の癖、保留事項は `docs/dev-notes.md` に書く。
- [ ] コストログの追記: Vertex AI経由のモデルを使った場合は `docs/cost-log.md` に記録する(月$10共有枠)。
