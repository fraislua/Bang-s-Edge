# discord-ai-hub MCP統合構想

## 0. 位置づけ

本書は**構想段階のメモ**であり、`docs/development-workflow.md`や`docs/audit-model-diversity-lessons.md`が定義する既存の監査運用を上書きするものではない。既存運用(agy内Gemini + Claude Codeによるモジュール監査)は本書の対象外で、そのまま維持する。

本書が扱うのは、新たに接続した`discord-ai-hub` MCPサーバー(`mcp__discord-ai-hub__ask`)を、既存のClaude Code(Opus5)+ agy(Antigravity CLI)体制にどう位置づけるか、という追加検討である。採用するかどうか・どこまで採用するかは未確定。

## 1. 前提として確認済みの事実(2026-09-10のセッションで実地検証)

### 1.1 discord-ai-hub MCP(`ask`ツール)
- テキストの一問一答のみ。ファイル添付・ツール実行不可。
- `session_id`指定時のみ短期履歴を保持(有効期限20分・最大20往復・プロセスメモリ上のみ)。
- モデル構成と課金:
  - ローカル(`google/gemma-4-12b-qat`他) — 無料・常時利用可
  - Vertex AI(`gemini-3.8-flash`・`xai/grok-4.6`) — **Discord bot側の人間利用と共有の月$10枠(Google Developer Program)を消費**。自動ブロックなし、使いすぎれば静かに枠を食う
  - OpenAI(`gpt-5.6-sol/terra/luna`) — **データ共有(Data Sharing)プログラム前提**。日次無料枠(Sol 25万トークン/日単独、Terra+Luna合計250万トークン/日)を超えると自動的に送信ブロックされ、金銭コストは発生しない
- 実機テスト: `--model`省略でローカルモデルへの疎通確認済み(2026-09-10)。
- **`compare(prompt, models, effort?, temperature?)`ツールが追加された(2026-09-10のサーバー更新)。** 同一プロンプトを複数モデルへ横並びで投げ、モデルごとの応答をJSON配列で返す。`session_id`は非対応(毎回独立呼び出し)。1モデルの失敗(無効ID・無料枠切れ・コンテキスト超過等)は他モデルの結果に影響しない。
  - **要注意**: `compare`の`models`配列にOpenAIモデル(`gpt-5.6-*`)を含めるかどうかは**サーバー側では一切フィルタ・警告されず、呼び出し側(Claude Code)の判断に委ねられている**(利用ガイド明記)。§3.3の境界線ルールを守るには、Sim層等アイデア性の高い内容を`compare`にかける際、こちらが`models`配列から`gpt-5.6-*`を明示的に除外する運用を徹底する必要がある。
- **Progress notifications(`notifications/progress`、約3秒間隔)が実装され、実機で166秒かかったローカルモデルeffort:High呼び出しの正常完了を確認済み(discord-ai-hub側の検証)。** ただしこれは`progressToken`を送るMCPクライアント側の対応が前提で、Claude Code自身がタイムアウトをどう延長するかはProject_Orbital側からはまだ未確認。
- **`models://registry`リソースが追加された。** `resources/read`で読めば、モデル一覧・コンテキスト長・データ共有有無・コスト特性を構造化データとして取得でき、本書§1.1の表よりも常に最新である。

### 1.2 Antigravity CLI(`agy.exe` v1.1.27)
- 実行ファイルは`agy`(PATH上は`AppData/Local/agy/bin/agy.exe`)。`which antigravity`ではヒットしない。
- 利用可能モデルにClaude Sonnet 4.6/Opus 4.6(Thinking)・Gemini 3.8/3.7/3.6 Flash・Gemini 3.1 Pro・GPT-OSS 120Bを含む(`agy models`で確認)。
- **`agy`のクラウドモデル呼び出しは、discord-ai-hubのVertex AI課金($10/月共有枠)とは別の課金系統**(Antigravity自体のサインイン・プランに基づく)と考えられる。両者を混同しないこと。
- **重要な既知の挙動**: ヘッドレス実行(`agy -p ...`)では、プロジェクトスコープ(`--new-project`等)を明示しない限り、カレントディレクトリの`.agents/agents/<name>/agent.md`(例: `norm-auditor`)を検出しない。素の`agy agent`は空リストを返し、`--agent norm-auditor`を指定しても存在しない名前を渡した場合と区別なく汎用アシスタント応答が返る(検証済み)。`agy --new-project --agent norm-auditor -p "..."`の形で初めて正しくペルソナが機能する。
- `--new-project`は実行のたびに新規プロジェクトエントリを作成する模様。繰り返し使う場合はAntigravity側のプロジェクト一覧が肥大化する可能性があり、後始末の要否は未検証。
- `agy changelog`によれば1.1.28が既にリリース済み(2026-09-10時点で1.1.27を使用中)。上記のヘッドレス挙動が新バージョンで変わる可能性はあるが未確認。

## 2. 課題認識(ユーザー提起、2026-09-10)

1. 既存の監査運用(`docs/design/`各モジュールをagy内Gemini 2本 + Claude Code 1本以上で監査)を、discord-ai-hub経由のVertex AIモデルにも毎回広げると、**月$10の共有予算を短期間で使い切るリスクが高い**。設計書一式(N1〜N40索引+対象design_m*.md全文+追補+PR差分)を毎モジュール送るような使い方は想定しない。
2. データ共有方針(ユーザーの整理): **コード(自分でも模倣・作成し得る部分)は外部送信して問題ない**。**アイデア・考え(設計意図・独自アルゴリズムの発想そのもの)は非公開にしたい**。
   - ただし本セッションの議論で、Vertex AI経由のGemini(Antigravity)には既に`design_m*.md`本文を丸ごと読ませる実績がある(§1既存監査運用)。この実績と整合させるなら、「アイデア非公開」の実務上の線引きは「Vertex AI vs OpenAI」ではなく、**「OpenAIのデータ共有枠(`gpt-5.6-*`)に何を送るか」**の一点に絞るのが妥当ではないか、という論点が出ている(結論は未確定)。
3. 大規模リファクタリング・通常の実装・通常の規範監査は、**引き続きagy + Claude Codeで行う方が良いのではないか**(ユーザー見解)。discord-ai-hub経由のクラウドモデルは、それらの代替ではなく別の狭い用途に絞る方向で検討したい。

## 3. 現時点で出ている構想(未確定・要合意)

### 3.1 役割分担の仮案

| 領域 | 担当(仮) | 理由 |
|---|---|---|

| 軽い壁打ち・生成 | discord-ai-hub経由のローカルモデル | 常時無料 |

### 3.2 「行き詰まった箇所」「OpenAIに出せない内容」の運用イメージ(たたき台)

- 呼び出すモデルは`xai/grok-4.6`のみを想定する。`gemini-3.8-flash`はagy経由で(長文脈込みで)既に使えるため、discord-ai-hub側でわざわざ同じ系統を呼ぶ理由がない。
- 対象は**設計書一式や差分全体ではなく、切り出した一つの疑問・一つの設計判断**に限定する。
- 例: 「この2つのアプローチのどちらが規範Nxの意図に近いか」「このアルゴリズムの計算量がO(n^2)になっていないか、別の視点で見てほしい」など、Claude Code自身の判断に迷いが残った1点を投げる形。
- コスト意識として、$10予算の消費ペースを人間側(ユーザー)が把握できるよう、利用時は都度ユーザーへの報告を挟むことが望ましいのではないか(未確定)。
- ローカルモデルとGrokの回答を並べて比較したい場合は`compare(models: ["google/gemma-4-12b-qat", "xai/grok-4.6"])`のような形も使える。**ただしSim層等アイデア性の高い内容を投げる場合は、`models`配列に`gpt-5.6-*`を絶対に含めないこと**(サーバー側は自動除外しないため、呼び出し側の責任)。

### 3.3 コード/アイデアの境界線(未確定の論点)

前回セッションの議論で出た仮説: 「コードかアイデアか」をasmdef境界で機械的に判定できるのではないか。
- `Sim/`(決定論の本体・独自アルゴリズム) → アイデアの実体とみなし、OpenAIデータ共有枠には送らない
- `Authoring/`・`Infra/`・`View/`・テストの定型部分 → 模倣されても問題ない「コード」とみなし、OpenAIデータ共有枠でも可

この境界線が実務上機能するかは未検証。特に`Sim/`以外にもゲーム性の核心(例: ウェーブ生成のパラメータ調整ロジックなど)が漏れ出す可能性があり、asmdef境界と「守りたい範囲」が完全一致するとは限らない点に注意が必要。

## 補遺: Bang's-Edgeでの検証状況(2026-09-10)

本構想の実地検証は`Bang's-Edge`リポジトリで実施することが確定した。検証専用の運用ルールは`docs/workflow.md`、ゲームコンセプト(アイデアの種、非公開)は`docs/game-concept.md`に定義した。

**agyカスタムエージェントは使わない方針に変更(2026-09-10、ユーザー判断)。** `.agents/agents/<name>/agent.md`のような常設定義ファイルは作らず、監査の観点をプロンプト文字列に埋め込む方式に切り替えた(詳細は`docs/workflow.md` §3)。

**§1.2・§4項目4/5への追記(実証結果)**: agy 1.1.28で検証したところ、`--new-project`も`--agent`も使わない`agy --model <model> -p "<prompt>"`は、Antigravityのプロジェクト状態ファイル(`~/.gemini/antigravity/antigravity_state.pbtxt`)を変更せず、プロジェクト一覧を汚染しない。この形ではカレントディレクトリのファイルを読めないが、`--add-dir "<絶対パス>"`を追加すればワークスペースとして機能し、ファイルを読めるようになる——かつこの場合も状態ファイルは変更されない。つまり**カスタムエージェントを使わない限り、`--new-project`によるプロジェクト一覧肥大化の問題自体が発生しない**。§4項目4(`--new-project`乱立問題)は、カスタムエージェント方式を採らないことで実質的に回避された。

進捗・知見は本ファイルの該当セクション(§1.2, §4, §6.2)に今後も追記していく想定。

**接続確認(2026-09-10、セッション再起動後)**: `discord-ai-hub`の`ask`・`compare`・`models://registry`いずれもBang's-Edgeプロジェクトスコープで正常動作を確認(ローカルモデルのみ使用、課金なし)。`models://registry`には本書§1.1未記載のローカルモデルが2種追加されていた(`gemma-4-e4b-uncensored-hauhaucs-aggressive`、`qwen/qwen3.8-27b`、いずれも無料・データ共有なし)。

**§4項目8(Progress notificationsの実効性)への回答(2026-09-10、実測)**: **Claude Code側のアイドルタイムアウトは、discord-ai-hubのProgress notificationsではリセットされない。** 3モデル(ローカル2種+`xai/grok-4.6`)にeffort=Highで`compare`を投げたところ、120秒でバックグラウンドタスクに移行した後、**326秒無応答として中断された**(`MCP server "discord-ai-hub" tool "compare" sent no response or progress for 326s; aborting`)。discord-ai-hub側が約3秒間隔でprogressを送る実装であっても、Claude Code側がそれをアイドル判定のリセットに使っていないか、`progressToken`が渡っていない。
- **対処法**(エラーメッセージが提示): MCP設定にper-serverの`timeout`(ms)を設定するか、環境変数`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`(ms、0で無効)を設定する。未設定のままでは長時間の`compare`は実質使えない。
- **実務上の回避策**: モデル数を減らし、effortを下げ、`ask`で単体モデルに投げる。今回は`ask`+`xai/grok-4.6`+effort=Mediumで問題なく完了した。ローカルモデルは推論が遅く(疎通確認時点でqwenが26秒)、`compare`に混ぜると全体を押し上げる要因になる。
- **本プロジェクトの方針(2026-09-10、ユーザー判断)**: タイムアウト問題の修正は本実験の終了後に行うこととし、**それまで`compare`は使わず、`ask`をモデルごとに個別に呼んで比較する**。

**§4項目7(`compare`の`gpt-5.6-*`除外をどう徹底するか)への影響**: 上記により本プロジェクトでは`compare`を使わないため、当初懸念していた「配列から除外し忘れる」というリスク構造自体が発生しない。`ask`は1回1モデルなので、送信のたびに「このモデルにこの内容を送ってよいか」を明示的に判断することになり、**判断が暗黙にならない**という副次的な利点がある。ただしこれは`compare`の除外運用が可能かどうかの検証にはならないため、その検証はProject_Orbital側で別途行う必要がある。
