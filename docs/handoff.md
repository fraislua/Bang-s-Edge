# セッション引き継ぎメモ

前回セッションの終了時点の状態と、次に着手できることをまとめたもの。**新しいセッションはまずこれを読むこと。** 詳細は各ドキュメントにあるので、ここには要点と「知らないとハマること」だけを書く。

## 1. 現在の状態

**ゲームは遊べる状態で公開済み。** → https://fraislua.github.io/Bang-s-Edge/

- リポジトリはpublic。`main`へpushすると数十秒でPagesに自動反映される。反映確認は公開ファイルを`curl`で取得し、改行コードを除いてローカルと比較する(Pagesは改行がLF、作業ツリーはCRLFになることがある)。

- ファイル構成: `index.html`(15行) / `style.css`(20行) / `config.js`(64行・全パラメータ) / `audio.js`(711行・Web Audio合成音) / `script.js`(1,075行・本体)。ビルド不要、外部ライブラリなし。

### 実測値(現行版)

- 盤面中央付近で普通に遊ぶと**約10秒**で発火。理想的に塊を追う操作で最速6秒台。
- ウィンドウサイズを320×240〜3440×1440(極端な横長・縦長含む)で変えても、最速タイムの幅は**0.32秒**(対策前4.0秒)。
- **10fps〜144fpsのすべてで発火**する(対策前は40fpsで0/10)。
- ユーザー環境(3440×1440・165Hz)で**ラウンドを通して165fps維持**(対策前は収束時28fpsまで下落)。
- ユーザーの評価: 「粒子が集まって前より見た目もゲーム性もよい」「**なかなかビッグバンが起きないのもゲーム性として面白い**」。

## 2. このプロジェクトの2つの目的

1. マウスのみで遊ぶブラウザゲームを作る(仕様: `docs/game-concept.md`)
2. **Claude Codeからどれだけタスクを分散できるかの実験**。Claude CodeはBrain(実装せず、分解・委任・検証・記録を担う)として動き、agyとdiscord-ai-hubに委任する。記録は`docs/model-experiment-log.md`。

## 4. 知らないとハマること(実測済み。詳細は`docs/dev-notes.md`)

### agy

- **agyの報告を信用しないこと。** 必ず`git status`・タイムスタンプ・ファイル内容で検証する。可能なら**挙動**で検証する(下記のNodeハーネス)。
- **書き込ませるには`--mode accept-edits`が必須。** 書き込ませたくない時は付けないことが安全装置になる。
- **ヘッドレスではターミナルコマンドを実行できない。** プロンプトに「ターミナルコマンドは実行せずファイル編集ツールのみで作業」と明記する。
- **基本形**: `agy --model <model> --mode accept-edits --add-dir "<リポジトリの絶対パス>" -p "[実装|監査] <対象>"`。`--new-project`と`--agent`は使わない。

### 検証

- **Chrome拡張が未接続で、ブラウザでの確認はできない。** 見た目・操作感・**描画性能**はユーザーに依頼する。**ユーザーの体感の言語化が唯一の観測手段**になる場面が多い。「いつ悪くなるか」「悪くなり続けるか止まるか」「何色になった時か」を聞くと原因を強く絞れる(実際にこれで`shadowBlur`を特定した)。
- **本物の`script.js`をNodeで動かして検証できる。** `vm`でconfig.js→script.jsを読み込み、`document`・Canvas・`requestAnimationFrame`をスタブすれば、本物の`update()`や`loop()`を回せる。**scratchpadのスクリプトはセッションをまたいで残らない**ので、次回は作り直す(手順は`docs/dev-notes.md`)。
- **検証そのものを疑うこと。** このプロジェクトで実際に踏んだもの:
  - パラメータ上書きが効いておらず「同じ条件を6回実行」していた → **上書きが効いたことを実行前にアサートする**
  - 画面隅で止まるポリシーで「動かすと損」と誤結論 → **測りたい変数以外を固定した対照を置く**
  - 塊の重心を毎フレーム正確に追う理想化モデルで「追従が+26%得」と誤結論 → **人間は常に微細に動く。静止ではなく微細振動を基準にする**
  - 1回の失敗から原因を推定しかけた → **再現を1回取ってから書く**
- **観測できない側の挙動を、手元の見え方だけで断定しない。** MCPサーバーへの報告で3件の原因推定を誤った。報告では「観測した事実」と「推定」を分けて書く。
- **Windows環境の注意**: Git Bashの`/tmp`とWindows版Pythonの`/tmp`は別の場所を指す(curlの結果はパイプで渡す)。Pythonの標準出力はcp932なので、日本語や記号を出すなら`PYTHONIOENCODING=utf-8`を付ける。bashヒアドキュメント→JSテンプレートリテラルでバックスラッシュが潰れる。

### 実装

- **環境非依存にするには、空間(論理盤面)と時間(固定ステップ)の両方を固定する。** 片方だけでは、描画負荷→fps低下→物理の破綻という経路でサイズ依存が残った。
- **`shadowBlur`は大きな図形やまとめたパスに使わない。** ぼかしはパス全体の外接矩形に掛かる。
- **`FIXED_DT`を1/120に上げてはいけない。** 実測でビッグバンが9.9秒→8.8秒とバランスが約10%変わり、全パラメータの再調整が要る。

## 5. 未解決・保留事項

1. **揺動(`WOBBLE_*`)の整理。** 導入の狙いだった「塊の芯を追う技術」は、理想化したモデルでしか成立しなかった。**微細振動を基準に振幅0と比較し、差がなければ定数ごと削る**のが素直。
2. **小さいウィンドウで文字と粒子が読めない**(論理盤面固定の副作用)。320×240では倍率0.167で判読不能。最小サイズの下限を設けるか未決定。
3. **165Hz表示では動きが60Hzに量子化される**(固定ステップの副作用)。ユーザーからの指摘は無し。気になるなら物理ステップ間を描画側で補間する。
4. **ゲームバランスは煮詰め途中。** 主な調整ダイヤルは`R_MAX_RATIO`(可動域の広さ)・`F_CREEP`(ラウンド長)・揺動振幅。ユーザーは「爆発しにくさ」を好意的に評価しているので、易しくする方向の調整は確認してから。
5. **音の再調整の余地。** 粒子が1点から塊になったので、視覚と音の対応が変わっている可能性がある。元々「妥協点として丁度良い」段階。
6. **`docs/game-concept.md`の未確定事項が2つ** — 「一度離したら即終了」で良いか、ビッグバン演出の作り込み度合い。
7. **MCPの未検証2点** — 「推論トークンだけで出力上限を使い切る経路」と「1モデルが326秒以上生成し続ける`compare`」。条件を作るのが難しく再現していない。
8. **構想段階(ユーザーは「今は行わない」と明言)**: unityroomへの投稿とランキング(ハイスコア+ビッグバンまでの最短時間の2本立て)。**unityroomはUnityのWebGLビルド専用**で、素のHTML/JSでは載せられない(Unityでの作り直しも選択肢とユーザーは言及)。HTML5のままならitch.io+自前バックエンド。論理盤面の固定で、タイムランキングの公平性という前提はクリア済み。最速タイムは理想的な操作で6秒台、普通に遊んで約10秒。

## 7. 実験で分かったこと(次回の委任判断に使う)

### 委任

- **仕様が数値まで確定していれば、軽量モデル(`gemini-3.8-flash-high`)で通る。** このプロジェクトで7回連続成功(643行の本体、反発・クラスタ配置、射程の可視化、論理盤面の固定など)。座標変換のように間違えると全体が壊れる実装でも、数式で指定すれば通った。
- **重いモデルの設計でも数式の整合性は必ず検算する。**
- **設計は高性能モデル・実装は軽量モデル**という分離が成立する。
- **数行〜十数行の修正は委任コスト(1回2〜4分)が見合わない**。Brainが直接編集する(固定ステップ化、描画修正、警告の持続判定などはBrainが実施)。
- **`gpt-5.6-sol`は数式の設計に強い。** 反発力の平衡個数を解析的に156個と予測し、実測158個とほぼ一致。設計相談はまずGPT系統(無料枠)を試す価値がある。
- **外部相談の回答が途中で切れていたら、切れた見出しの中身を取りに行く。** 切断された節(明示的オイラー法の安定限界)が、そのまま後の欠陥(60fps未満で爆発しない)だった。現在はサーバーが`[⚠`注記を付けるので気づきやすくなった。

### ユーザーとの協働

- **欠陥の多くは、ユーザーの体感が先に捉えていた。** 「動かすと時間がかかり毎回同じ」→ストップウォッチ化、「人間は常に微細に動く」→検証基準の誤り、「画面サイズで体験が違う」→空間の非依存化、「大きい画面でガクガクして収束が遅い」→fps依存の物理破綻と描画コスト。**Brainの数値検証は、ユーザーの体感を確かめて定量化する役割のときに最も効いた。**
