# discord-ai-hub への報告 — 実運用で判明した問題と改善提案

Bang's-Edge プロジェクトで `ask` を実際に設計相談に使った結果、判明した問題をまとめる。回答の**品質そのものは非常に高く**(後述)、以下はすべて「良い回答を確実に受け取るための」インフラ側の問題である。

優先度は **B > A > C > D**。B は実際に本番コードの欠陥を1件通過させた。

---

## B. 応答が無言で切り捨てられる(最優先・実害が発生した)

### 現象

`ask` の応答が**数式の途中で唐突に終わり、切り捨てられた旨の表示が一切ない。** 呼び出し側からは、モデルがそこで書き終えたのか、上限で切られたのかを区別できない。

### 再現条件

| 項目 | 値 |
|---|---|
| モデル | `gpt-5.6-sol` |
| effort | Medium |
| プロンプト長 | 約2,900文字(見出しA〜Dの4問構成) |
| 結果 | 見出し `B-4` の数式の途中で切断。**見出し C と D は丸ごと欠落** |

同じ内容を「欠落したCとDだけ」に絞った短いプロンプト(約1,200文字)で投げ直すと、**完全な形で、しかも120秒以内に返った。** 出力長の上限に当たっていると考えられる。

### 実害(この報告で最も重要な部分)

切断された `B-4` の見出しは **「明示的オイラー法・dt=1/60 で安定に保てる反発係数 K の上限はどう見積もるか」** だった。モデルは安定条件

```
ω_max² dt² < 2(1+γ)/γ
```

の右辺を計算し始めたところで切れていた。

**この欠落部分が扱おうとしていた問題が、そのまま本番の欠陥になった。** 実装後の検証で、フレームレートが60fpsを下回ると硬い反発力を明示的オイラー法が解けなくなり、**ビッグバンが一度も起きなくなる**(40fps相当で0/10、30fpsで0/10)ことが判明した。物理を固定ステップ化して修正済みだが、**切断が明示されていれば、欠けた節を取りに行った可能性が高い。**

切断されたこと自体には気づいており記録もしていたが、「回答が途中で切れた」としか認識できず、**欠けた部分が何を論じようとしていたかまでは辿らなかった。** 切断が明示されていれば扱いが変わっていた。

### 提案する修正

1. **切り捨てが発生したことを応答に明示する。** 上流APIの `finish_reason`(`length` / `stop` / `content_filter` 等)に相当する情報を、応答テキストとは別に返す。テキスト末尾に `[応答が長さ上限で切り捨てられました]` と付記するだけでも実用上は十分。
2. **継続取得の手段を用意する。** 同じ `session_id` で「続きを」と頼めば続きが返る、という運用が確実に機能するなら、その旨をツール説明に書く。
3. **出力長の上限値をツール説明に明記する。** 呼び出し側が事前に質問を分割する判断ができる。

## A. `ask` が正常終了扱いで空文字列を返す

### 現象

呼び出しは**成功として完了し完了通知も届くのに、応答本文が空文字列**だった。エラーメッセージも理由の記載もない。

### 再現条件

| 項目 | 値 |
|---|---|
| モデル | `gpt-5.6-sol` |
| effort | **High** |
| プロンプト長 | 約2,600文字 |
| session_id | 指定あり(文字列) |
| 経過 | 120秒でバックグラウンドタスクへ移行 → 完了通知は届いた → `<result>` が空 |

**同じ内容を effort=Medium で投げ直すと成功した**(この時に上記Bの切り捨てが起きた)。effort=High 固有の経路を疑っている。試行回数が1回のみのため、High が原因と断定はできていない。

なお過去にも `xai/grok-4.6` で「effort=High の `compare` が失敗 → effort=Medium の `ask` で成功」という同じ形の経路を辿っており、**High で不安定になる傾向がある可能性**がある。

### 影響

呼び出し側が **「成功したが中身が無い」を失敗と区別できない。** リトライすべきか、モデルが本当に何も答えなかったのか判断できない。自動化された運用では静かに空のまま次の処理に進んでしまう。

### 提案する修正

1. **空応答はエラーとして返す。** 成功として空文字列を返さない。
2. **空になった理由を含める**(上流のエラー、コンテンツフィルタ、トークン上限、タイムアウト等)。
3. **effort=High の経路を調査する。** 特に、長時間実行のバックグラウンド処理で結果の受け渡しが失われていないか。

## C. `compare` のタイムアウト(既知・未修正)

前回セッションで報告済みの内容の再掲と補足。

### 現象

3モデル(ローカル2種 + `xai/grok-4.6`)に effort=High で `compare` を投げたところ、**326秒無応答として中断された。**

```
MCP server "discord-ai-hub" tool "compare" sent no response or progress for 326s; aborting
```

### 分かっていること

- **discord-ai-hub 側の Progress notifications(約3秒間隔)は、Claude Code 側のアイドルタイムアウトをリセットしない。** サーバー側で実装済みでも、クライアントがそれをアイドル判定に使っていないか、`progressToken` が渡っていない。
- **ローカルモデルは推論が遅く、`compare` の総時間を押し上げる。** 疎通確認時点で qwen 単体が26秒かかっていた。遅い1モデルが全体を待たせる構造になっている。
- サーバー側では処理が進んでいた可能性があり、**中断されても Vertex AI の枠を消費した可能性がある**(課金面のリスク)。

### 提案する修正

1. **`ask` と同様にバックグラウンドタスクへ移行できるようにする。** 後述するとおり `ask` の挙動は非常に良く、`compare` だけが中断されるのは一貫性を欠く。
2. **モデルごとに完了次第、部分結果を返す。** 全モデルの完了を待つ設計だと、最も遅い1モデルが全体を人質に取る。
3. **中断時に、サーバー側の処理が継続しているか・課金枠を消費したかを呼び出し側が知る手段を用意する。**

## D. 引数の型検証が緩く、事故を誘発する

### 現象

`ask` のスキーマは以下のようになっている。

```
required: ["prompt", "model", "session_id", "effort", "temperature"]
session_id:  type: ["string", "null"]
temperature: type: ["number", "null"]
```

**`session_id` と `temperature` が required かつ nullable** であるため、「使わないが何か渡さなければならない」状況が生まれる。

実際に本プロジェクトの呼び出しでは、**`temperature` に文字列 `"null"` を、`session_id` にも文字列 `"null"` を渡してしまい、どちらもエラーにならずに通った。** `temperature` は `["number", "null"]` と宣言されているので、文字列 `"null"` は本来バリデーションエラーになるはずである。

### 影響

- `session_id: "null"` は、**`null` という名前のセッションを実際に作ってしまった可能性がある。** そうであれば、独立した呼び出しのつもりが意図せず履歴を共有し、しかもそれが**他の利用者と衝突しうる**(誰でも同じ事故を起こすため、`"null"` という共有セッションに複数の会話が混ざる)。
- `temperature: "null"` が無視されたのか、`NaN` として解釈されたのかが不明。上記 A の空応答との関連は否定できていない(3回すべて同じ渡し方をしており、うち成功2回・失敗1回なので、これ単独が原因ではない)。

### 提案する修正

1. **`session_id` / `effort` / `temperature` を `required` から外す。** 省略時のデフォルトが定義されているのだから、必須にする理由がない。これが最も確実な解決になる。
2. **型検証を厳格にする。** 宣言と異なる型は明確なエラーで弾く。
3. 上記が難しい場合、少なくとも **文字列 `"null"` / `"undefined"` / `""` を `null` として正規化する**か、明示的に拒否する。

## E. 良かった点(この挙動は維持してほしい)

問題点だけでは判断を誤らせるので、有効だった点も記録する。

- **`ask` が120秒でバックグラウンドタスクへ移行し、セッションが中断されずに作業を継続できた。** 完了時には通知が届く。この間に別の作業(数値シミュレーション)を進められたため、**待ち時間が実質的にゼロになった。** 上記Cの `compare` が中断されるのとは対照的で、この設計は非常に有用。
- **短いプロンプトへの応答は120秒以内に完結する。** 質問を分割すれば切り捨ても待ち時間も回避できる。
- **回答の品質は非常に高かった。** `gpt-5.6-sol` は、粒子間反発の平衡状態を六方充填と静水圧平衡から解析的に導き、**「半径40px内の平衡個数 ≈ 156個」と予測した。こちらの数値シミュレーションによる実測値は158個で、ほぼ一致した。** さらに「位置を更新後の速度で進めているか(semi-implicit)、真の forward Euler か」で安定な係数が変わると自ら条件分岐しており、前提条件の詰め方も的確だった。**インフラ側の問題さえ解ければ、設計相談の用途で十分に実用的である。**

## 優先度まとめ

| 優先度 | 項目 | 理由 |
|---|---|---|
| **最高** | B. 切り捨ての無言化 | **実際に本番の欠陥を1件通過させた。** 呼び出し側が対処できない |
| **高** | A. 空応答が成功扱い | 成功と失敗を区別できず、リトライ判断ができない |
| 中 | D. 引数の型検証 | 事故が起きやすく、セッションの意図しない共有につながりうる |
| 中 | C. `compare` のタイムアウト | 回避策(`ask` を個別に呼ぶ)が確立しているため運用は可能 |

BとAはいずれも **「失敗が失敗として見えない」** という同じ性質を持つ。呼び出し側は自己申告を検証できないため、**サーバーが正直に失敗を報告することが、この統合全体の前提**になる。
