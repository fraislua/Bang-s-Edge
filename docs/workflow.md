# Bang's-Edge — 開発・監査運用ルール

## 0. 位置づけ

本書は、discord-ai-hub MCP統合構想(`docs/concept-ai-hub-integration.md`、元はProject_Orbitalで作成)の実地検証として、このリポジトリで採用する**軽量な運用ルール**を定義する。Project_Orbitalの`docs/development-workflow.md`のような大規模なN1〜N40規範は本プロジェクトには存在しない。ここでは検証に必要な最小限のルールのみを定める。

## 1. データ共有方針(2026-09-10に範囲を緩和)

本プロジェクトは実験目的のため、**「明らかにユーザーのアイデアと分かるもの」以外は共有可**とする(ユーザー判断)。当初は`docs/game-concept.md`全体を非公開としていたが、実装仕様まで一律に禁じるとGPT系統をほとんど活用できず、実験の幅が狭まるため。

- **非公開(`gpt-5.6-*`に送らない)**: *赤い粒子をマウスの長押しで集め、ビッグバン直前に離して密度を競う*という発想の組み合わせと、タイトル`Bang's-Edge`。`docs/game-concept.md`の「概要」「ゲームメカニクス」「スコアリング」「ラウンド構造」。
- **共有可**: 同ファイルの「実装仕様」(密度の数式・各パラメータ・音響設計)、実装コード、一般的な技術相談、定型作業、ドキュメント整備。
- **判断基準**: そのプロンプトだけを読んで「どんなゲームか」が復元できてしまうかどうか。復元できるなら`models`配列から`gpt-5.6-*`を外す。
- ローカルモデル・Vertex AI(`xai/grok-4.6`等)・agy経由のモデルには、`docs/game-concept.md`全体を渡してよい。
- 本プロジェクトでは`compare`を使わない(§2参照)。`ask`は1回につきモデルが1つなので、「このモデルに、この内容を送ってよいか」を毎回明示的に判断することになる。

## 2. モデル別の役割分担(2026-09-10更新: タスク分散実験のため役割拡張)

**方針転換**: 本プロジェクトは「Claude Codeからどれだけタスクを分散させられるか」を確かめる実験を兼ねる。実装フェーズはClaude CodeをOpus5(Brain)として動かし、実装そのものは極力agy/discord-ai-hubに委任する(Claude Codeは分解・委任先決定・検証・記録が主務)。Opus5への切り替えはユーザー側の操作が必要(§3参照)。

| 用途 | 使用先 | 備考 |
|---|---|---|
| タスクの分解・委任先決定・検証・記録 | Claude Code(Brain、Opus5) | 実装そのものは極力自分で書かない方針 |
| 実装・監査(いずれもagyへ委任) | agyへのヘッドレス呼び出し(`--add-dir`、カスタムエージェント不使用) | §3参照。同一系統に実装と監査を両方頼むため「自己監査」になる場面があるが、今回は意図的に許容し結果を観察する実験設定(2026-09-10、ユーザー判断) |
| 行き詰まった一点だけ別視点が欲しい(非公開情報を含まない) | discord-ai-hub経由 `xai/grok-4.6` | 月$10共有枠(Vertex AI)を消費するため、設計書一式のような大きな投げ方はしない。1つの疑問に絞る |
| **技術相談・設計案・コード生成(今後は積極的に活用する)** | discord-ai-hub経由 `gpt-5.6-*`(Terra/Luna優先、深い検討はSol) | **2026-09-10方針: ユーザーがGPT系統の回答にも関心を示したため、今後は活用していく。** 日次無料枠が大きく(Terra+Luna合計250万トークン/日、Sol 25万/日)金銭コストがゼロなので、Vertex AI枠を使う前にまずここを試す価値がある。§1の判断基準に従い、ゲームの発想が復元できない形に抽象化して送ること |
| 軽い壁打ち・生成 | discord-ai-hub経由 ローカルモデル(`google/gemma-4-12b-qat`等) | 常時無料 |
| 複数モデルの回答を比較したいとき | discord-ai-hub `ask` を**モデルごとに個別に呼ぶ** | **`compare`は本プロジェクトでは使わない**(2026-09-10、ユーザー判断)。3モデル×effort=Highで326秒無応答となりタイムアウトしたため。ツール側の問題は実験終了後に修正予定で、それまでは`ask`を複数回呼ぶ形で代替する |

モデル・effortの具体的な選択は`docs/model-experiment-log.md`の過去実績を参考にする(§4)。

## 3. Brainからagyへの委任フロー(カスタムエージェント不使用・プロンプト側で縛る方式)

**Opus5(Brain)への切り替えについて**: Claude Code自身のモデル切り替え(Sonnet5→Opus5)はユーザー側の操作(`/model`等)が必要で、このドキュメントやCLAUDE.mdを置くだけでは切り替わらない。実装フェーズに入るタイミングでユーザーに切り替えてもらう前提を書いているだけで、Claude Code自身がここを読んで自動的にモデルを変えることはできない。

**方針(2026-09-10確定)**: `.agents/agents/<name>/agent.md`のような常設のカスタムエージェント定義ファイルは作らない。理由は、agyのカスタムエージェント検出には`--new-project --agent <name>`が必要で、`--new-project`を使うたびにAntigravity側のプロジェクト一覧が肥大化する(構想メモ§1.2既知の問題)ため。代わりに、依頼する役割(実装/監査)・観点を**プロンプト文字列側に埋め込み**、`--add-dir`でカレントディレクトリをワークスペースとして渡すことで、`--new-project`・`--agent`のどちらも使わずに実行する。

**実証済み(2026-09-10、agy 1.1.28)**:
- `agy --model <model> -p "<prompt>"`(`--new-project`も`--agent`も無し)は、Antigravityのプロジェクト状態ファイル(`~/.gemini/antigravity/antigravity_state.pbtxt`)を変更せず、プロジェクト一覧を汚染しない。
- ただしこの形ではカレントディレクトリのファイルを読めない(ワークスペース未指定のため)。
- `--add-dir "<カレントディレクトリの絶対パス>"`を追加すると、指定ディレクトリ内のファイルを読めるようになり、かつ状態ファイルは変更されない(プロジェクト一覧を汚染しない)。
- **実装を委任する(ファイルを書かせる)場合は`--mode accept-edits`が必要**(2026-09-10実証)。これを付けるとヘッドレスでも編集が自動承認され、承認待ちで停止しない。読むだけの監査呼び出しには不要。

**追加実証(2026-09-10)**: `--add-dir "<絶対パス>"` を付けると、そのディレクトリの `AGENTS.md` が `--new-project`・`--agent` 無しでも自動的に読み込まれる(ペルソナ・品質基準がプロンプト無しで反映されることを確認済み)。そのため、実装・監査共通の基本ペルソナ・品質基準は本プロジェクトルートの `AGENTS.md` に持たせてあり、呼び出し時の`-p`には**役割(実装/監査)と対象の指定だけ**書けばよい。

**呼び出し例(監査)**:
```
agy --model gemini-3.8-flash-high --add-dir "C:\Users\ryoga\Documents\Bang's-Edge" -p "[監査] index.html / script.js のパーティクル集積ロジックをレビューしてください。"
```

**呼び出し例(実装委任)**:
```
agy --model claude-opus-4-6-thinking --add-dir "C:\Users\ryoga\Documents\Bang's-Edge" -p "[実装] docs/game-concept.mdの仕様に従い、パーティクルの集積範囲・強さの計算ロジックをscript.jsに実装してください。"
```

モデル・effortは呼び出しごとに選択し、`docs/model-experiment-log.md`の過去実績を参考にする。プロンプト冒頭に`[実装]`/`[監査]`のように役割を明示すると、AGENTS.mdの基本方針(実装時/監査時で挙動を分けている)と噛み合いやすい。レビュー観点・実装前提そのものを変えたい場合は`AGENTS.md`を編集する(プロンプト側で都度上書きも可能)。

**フロー**:
1. Brain(Claude Code)がタスクを機能単位に分解し、委任先(agy/discord-ai-hub/自分自身)とモデル・effortを決める(`docs/model-experiment-log.md`の過去実績を参考にする)。
2. 委任した場合は上記の形で`agy --add-dir ... -p "[実装]/[監査] ..."`を実行する(自分で実装する場合はこのステップを省略)。
3. 結果を検証し、`docs/model-experiment-log.md`に結果(成功/部分的/失敗)と選択理由を追記する。
4. 指摘・不備があれば修正を依頼し、収束するまで1〜3に戻る。
5. 何往復で収束したか、モデル・effortによる出来の差を観察し、`docs/concept-ai-hub-integration.md` §1.2/§4に知見を追記する。

## 4. モデル選択と実験ログ(自己改善サイクル)

- 委任前に`docs/model-experiment-log.md`を確認し、類似タスクの実績(例: 「Luna-Mediumでは失敗したがLuna-XHighでは成功した」等)があれば選択の参考にする。
- 委任後は結果と選択理由を同ログに追記する(後回しにしない)。
- 「結果に基づいて次の選択に反映する」というサイクルは、今回は**Brain(Claude Code)が毎回ログを読んで判断する運用ルール**として実現する。成功率の自動集計・自動選択のような統計的な仕組みは今回は導入しない(2026-09-10、ユーザー判断: 本番環境で必要になった時点で別途検討する)。
- ログが十分溜まったら、傾向を本書§2の役割分担表に手動で反映し直す。

## 5. コスト報告

- discord-ai-hub経由でVertex AI(`xai/grok-4.6`)を呼ぶたびに`docs/cost-log.md`へ記録する。
- 月$10予算に対する消費ペースを把握するため、記録は都度・後回しにしない。

## 6. 検証後に持ち帰る情報(構想メモ§6.1に対応)

- データ共有の線引きの運用可否 → 当初の検証項目は「`compare`の`models`配列から`gpt-5.6-*`を除外し忘れないか」だったが、本プロジェクトでは`compare`自体を使わない方針になったため、**`ask`でモデルを1つずつ指定する運用で判断漏れが起きるか**に読み替えて記録する。
- agyとの往復フローの実用性 → 往復回数・`--new-project`肥大化の実害有無。
- コスト実測 → `docs/cost-log.md`の記録から$10予算消費ペースを算出。

結果は`docs/concept-ai-hub-integration.md`の該当セクション(§4, §6.2)へフィードバックする。
