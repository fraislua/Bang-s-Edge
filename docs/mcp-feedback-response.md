## 項目ごとの回答

### B. 応答が無言で切り捨てられる

**原因**: OpenAI系モデルの出力上限(`max_completion_tokens`)が8,192で、OpenAIではこの上限に
**推論トークンも含まれます**。報告の呼び出しは「推論4,730+本文3,462=8,192」で上限に達していました。
さらにサーバーが、上流から届いていた終了理由(`finish_reason: length`)を捨てていたため、切り捨てを
伝えられていませんでした。

**修正**:
- OpenAI系(gpt-5.6-sol/terra/luna)の出力上限を32,000に引き上げ(Gemini/Grokは8,192のまま)
- 途中で終わった応答には、本文の末尾に次の注記が付きます
  ```
  [⚠ 応答は出力上限に達して途中で切れています(finish_reason=length、出力トークン=…、推論トークン=…、出力上限=32000)。…]
  ```
- `compare` は各モデルの結果に `finishReason` と `warning` を追加

**呼び出し側で変えること**: ask応答の末尾に `[⚠` で始まる注記がないか、compare結果の `warning` が
null でないかを確認してください。注記があれば本文は不完全です。同じ `session_id` で続きを頼めますが、
推論モデルは続きの生成でも推論し直すため確実ではありません。長い回答が必要な問いは、最初から分割するのが確実です。

### A. 成功扱いで空文字列が返る

**原因**: Bと同じです。effort=High の呼び出しは推論だけで8,192トークンを使い切り(推論8,192=出力8,192)、
本文が0トークンでした。サーバーは183秒で空文字列を正常終了として返しています。
**High固有の不安定さでも、120秒でのバックグラウンド移行で結果が失われたのでもありません。**
傍証に挙げられていた「grok-4.6 で High の compare が失敗」は、下記Cの中断のことで、grok は呼ばれる前でした。

**修正**: 本文が空の応答はエラー(`isError: true`)にし、終了理由とトークン内訳を返します。出力上限に
達していた場合は「推論だけで出力上限を使い切った可能性が高い」と案内します。空の応答は `session_id` の
履歴にも残しません。

**呼び出し側で変えること**: このエラーが出たら、effort を下げるか問いを分割して再試行してください。

### C. compare のタイムアウト

**原因**: サーバー側です。compare は**モデルを切り替えるときにしか進捗通知を送っておらず**、1モデルの
生成中は無通知でした。報告の呼び出しでは、2番目の qwen の生成中に326秒間無通知となり中断されています。
サーバー側で処理が止まったのは開始から399秒後で、差の73秒は、qwen 開始時の進捗通知でアイドル判定が
リセットされていたことを示します。つまり **Claude Code は進捗通知でタイマーをリセットしています**
(「リセットしない」という分析は誤り)。ask にも、推論中は無通知になる同じ潜在問題がありました。

中断による Vertex AI 枠の消費はありません(3番目の grok は呼ばれる前に中断され、サーバー側の処理も
中断の時点で止まっています)。

**修正**: 進捗通知を、モデルからのデータ到着とは無関係に約3秒ごとに送るよう変更しました(ask・compare
の両方。推論中や最初のトークン待ちの間も途切れません)。本文0文字のまま55秒推論し続けた呼び出しでも、
3秒間隔で通知が届くことを実機で確認済みです。

**呼び出し側で変えること**: compare を避ける必要はなくなりました。ただしモデル単位のタイムアウトは
設けていないため、全体の所要時間は最も遅いモデル次第です。

### D. 引数の型検証が緩い

**確認結果**: 「全引数が required かつ nullable」はその通りでした。一方、**文字列 `"null"` が通った件は
再現しませんでした。** サーバーログでは、報告の3回の `session_id` は `"bangs-edge-repulsion-design"` と
本物の null(2回)で、文字列 `"null"` は届いていません。修正前のサーバーも `temperature: "null"` は
拒否していたため、成功した3回の呼び出しで文字列が渡っていたとは考えにくく、**`"null"` という共有
セッションは作られていません**。クライアントの表示で null が `"null"` と見えていた可能性があります。

**修正**:
- 省略可能な引数を `required` から外しました(ask は `prompt` のみ、compare は `prompt` と `models` のみ必須)
- 呼び出し前に引数を定義に照らして検証し、必須引数の欠落・未知の引数名・型の不一致は、
  どの引数がなぜ不正かを示すエラーにします(従来は理由なし)
- `model`/`session_id`/`effort` の文字列 `"null"`・`"undefined"`・空文字は省略として扱います。
  `temperature` に文字列を渡すとエラーです(`"0.5"` のような数値の文字列も不可)

**呼び出し側で変えること**: 使わない引数は渡さずに省略してください。

### E. 良かった点について

120秒でのバックグラウンドタスクへの移行は、Claude Code 側の機能です(サーバー側の実装ではありません)。

### 追加で観測したこと(サーバー側で確認してほしい)

**compare 内の qwen が `finish_reason` 無しの空応答で終わった。**

- **観測**: `qwen/qwen3.8-27b`(effort=High)が154秒後に「応答本文が空でした(finish_reason=(なし))」。
- **観測**: 同じ質問を qwen に単独で投げ直すと、effort 省略・effort=High のいずれも正常に回答した(各1回)。**effort=High だけでは再現しない。**
- **観測**: qwen が生成していた時間帯に、Bang's-Edge 側から**別のローカルモデル(gemma 12B と gemma E4B)への `ask` を並行して送っていた**。
- **推定(未確認)**: 同じ LM Studio 上でモデルの切り替えが起き、qwen の生成が途中で打ち切られた。「自然に書き終えた `stop`」ではなく「`finish_reason` 無し」だった点と整合する。**サーバーまたは LM Studio のログで、この時刻にモデルのロード/アンロードがあったか確認してほしい。**
- **提案**: `finish_reason` が無いまま終わった場合は、「生成が途中で打ち切られた可能性」を明示すると、呼び出し側が「モデルが何も書かなかった」のか「外部要因で止まった」のかを区別できる。

### ツール定義の表示について(サーバー側は正常・クライアント側の問題)

- **観測**: サーバーに JSON-RPC で直接 `tools/list` を問い合わせると、`ask` は `required: ['prompt']`、`compare` は `required: ['prompt', 'models']` を返した。**修正は正しく反映されている。**
- **観測**: 一方、`/mcp` での再接続とセッションの起動し直しの後も、Claude Code がこちら(モデル)に提示するツール定義は、5引数すべて必須のままだった。
- **推定**: Claude Code 側が古い取得結果のツール定義を保持している。**MCPサーバー側の対応は不要。**
- **実務上の影響は無い**: クライアントの都合で全引数を渡す必要があるが、使わない引数に `null` を渡せばサーバーは省略として扱う(今回の検証呼び出しはすべてこの形で行い、正常に動作した)。

### Bang's-Edge 側の認識の訂正

- `gpt-5.6-sol` の出力上限32,000は**受付判定で見込む分であって、1回ごとに消費される量ではない**(集計は実使用量)。「Solは数回で尽きる」という当初の理解は誤りだった(ユーザー指摘)。
